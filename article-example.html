WireGuard VPN: Full Setup Guide

Category: Networking · Posted: 2025-05-18 · Updated: 2025-05-20 · ~12 min read
Article Info
TopicNetworking
Kernel≥ 5.6
Tested onArch, Debian 12
DifficultyIntermediate
Updated2025-05-20

WireGuard is a modern, minimal VPN protocol built into the Linux kernel since 5.6. It is dramatically simpler than OpenVPN or IPsec — roughly 4,000 lines of code — and achieves better throughput with lower latency by using state-of-the-art cryptography (ChaCha20, Poly1305, Curve25519, BLAKE2).

This guide covers a full production setup: generating keys, configuring a server and client, enabling split tunneling, and adding a systemd-based kill switch that drops all traffic if the VPN goes down.

1 Prerequisites

  • A server with a public IP (VPS or home server with port forwarding)
  • Linux kernel ≥ 5.6 on both ends (check with uname -r)
  • Root or sudo access
  • UDP port 51820 open on the server firewall
⚠ Note If you are running a kernel older than 5.6, install the wireguard-dkms out-of-tree module instead of using the built-in one. Instructions differ slightly.

2 Installation

2.1 Arch Linux

WireGuard tools are in the official repository:

terminal
$ sudo pacman -S wireguard-tools

2.2 Debian / Ubuntu

terminal
$ sudo apt update
$ sudo apt install wireguard wireguard-tools

3 Key Generation

WireGuard uses Curve25519 key pairs. Generate separate pairs for the server and each client. Keys are just base64 strings — keep private keys private.

terminal – server
$ umask 077   # ensure private key is readable only by root
$ wg genkey | tee /etc/wireguard/server_private.key | wg pubkey > /etc/wireguard/server_public.key
$ cat /etc/wireguard/server_private.key   # copy this value
terminal – client
$ wg genkey | tee client_private.key | wg pubkey > client_public.key
ℹ Tip You can also generate a pre-shared key for an extra layer of symmetric encryption between a specific peer pair: wg genpsk > psk.key

4 Server Configuration

Create /etc/wireguard/wg0.conf on the server. Replace SERVER_PRIVATE_KEY and CLIENT_PUBLIC_KEY with your actual key values. 10.0.0.1/24 is the VPN subnet — choose any RFC 1918 range that doesn't conflict with your local network.

/etc/wireguard/wg0.conf (server)
[Interface]
Address    = 10.0.0.1/24
ListenPort = 51820
PrivateKey = <SERVER_PRIVATE_KEY>

# Enable IP forwarding and NAT so clients can route through the server
PostUp   = iptables -A FORWARD -i %i -j ACCEPT; iptables -A FORWARD -o %i -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i %i -j ACCEPT; iptables -D FORWARD -o %i -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

[Peer]
# Client 1 – laptop
PublicKey           = <CLIENT_PUBLIC_KEY>
AllowedIPs          = 10.0.0.2/32

Enable IP forwarding persistently:

terminal
$ echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-wireguard.conf
$ sudo sysctl -p /etc/sysctl.d/99-wireguard.conf

Enable and start the interface:

terminal
$ sudo systemctl enable --now wg-quick@wg0

5 Client Configuration

/etc/wireguard/wg0.conf (client)
[Interface]
Address    = 10.0.0.2/24
PrivateKey = <CLIENT_PRIVATE_KEY>
DNS        = 1.1.1.1, 9.9.9.9

[Peer]
PublicKey  = <SERVER_PUBLIC_KEY>
Endpoint   = your.server.ip:51820
AllowedIPs = 0.0.0.0/0   # route ALL traffic through VPN
PersistentKeepalive = 25
✓ Test connectivity After bringing up the client with sudo wg-quick up wg0, verify with ping 10.0.0.1 and check your public IP at curl ifconfig.me — it should now show the server's IP.

6 Split Tunneling

With split tunneling, only specific traffic goes through the VPN. Change AllowedIPs on the client to list the specific subnets you want routed through the tunnel rather than 0.0.0.0/0.

Split tunnel example — only 10.x and 192.168.1.0/24 go through VPN
AllowedIPs = 10.0.0.0/8, 192.168.1.0/24

The inverse — "everything except certain subnets" — requires using the AllowedIPs calculator to produce the correct CIDR complement.

7 Kill Switch

A kill switch blocks all internet traffic if the VPN drops, preventing accidental exposure. The cleanest approach on modern Linux uses wg-quick's built-in firewall marks and a routing rule.

/etc/wireguard/wg0.conf — add to [Interface]
PostUp   = ip rule add not fwmark 51820 table 51820; ip route add blackhole default metric 6700 table 51820; ip6tables -A OUTPUT ! -o %i -m mark ! --mark $(wg show %i fwmark) -m addrtype ! --dst-type LOCAL -j REJECT
PostDown = ip rule del not fwmark 51820 table 51820; ip route del blackhole default metric 6700 table 51820; ip6tables -D OUTPUT ! -o %i -m mark ! --mark $(wg show %i fwmark) -m addrtype ! --dst-type LOCAL -j REJECT
⚠ Note on DNS leaks With a kill switch, ensure your DNS servers (1.1.1.1, etc.) are reachable only through the tunnel, or use a private DNS server inside the VPN. Systemd-resolved may still leak queries if misconfigured.

8 Troubleshooting

8.1 Check interface status

terminal
$ sudo wg show

Look for latest handshake in the peer section. If missing, the peers can't reach each other — check firewall rules and the Endpoint address.

8.2 Common issues

  • No handshake — UDP 51820 blocked on server. Check iptables -L and cloud firewall rules.
  • Handshake succeeds, no traffic — IP forwarding not enabled, or PostUp NAT rules not applying. Check sysctl net.ipv4.ip_forward.
  • DNS not working — Confirm DNS = line in config and that resolvconf or systemd-resolved is managing /etc/resolv.conf.
  • High latency — Try adjusting PersistentKeepalive. Lower values (15–25s) help behind strict NAT.
